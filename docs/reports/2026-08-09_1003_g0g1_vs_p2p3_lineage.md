# G0/G1 vs P2/P3 lineage and metric-difference root cause

Scope: read-only investigation of the Track B pooled news-GNN pilot
(`baselines/2026-08-08_pooled_news_gnn_ablation_baseline/`). G0/G1 code read from the
committed branch `feature/masked-gnn` @ `0b95108` via `git show` (the `.worktrees/masked-gnn`
working copy was not entered). Result JSONs read from the `.worktrees/graph-viz` worktree, which
holds both the pooled P0–P3 runs and the G0/G1 graph runs.

---

## Question 1 — Are G0/G1 derived from P2/P3?

Yes. G0/G1 are not a separate model; they are a thin wrapper around a **P3** backbone.

- `GraphAblationModel.__init__(self, p3: PooledPriceNewsLSTM, use_gnn: bool)`
  (`code/models.py:157`) takes a `PooledPriceNewsLSTM` and **reuses its components directly**:
  `self.price_encoder = p3.price_lstm`, `self.news_encoder = p3.news_lstm`,
  `self.gate_logits = p3.gate_logits`, `self.head = p3.head` (`models.py:161-165`). All of these
  are **frozen** (`requires_grad_(False)`, `models.py:170-174`).
- The forward pass runs the P3 encoders under `torch.no_grad()`, applies the **per-ticker news
  gate** `torch.sigmoid(self.gate_logits[ticker_ids]) * news_hidden` (`models.py`, forward), then
  concatenates `[price_hidden, gated_news]` exactly as `PooledPriceNewsLSTM.forward` does.
- Because `gate_logits` is present and used, the wrapped backbone is the **gated** variant, i.e.
  **P3** (`use_gate=True`), not P2. `from_p3_checkpoint` builds the inner model with
  `use_gate=True` (`models.py`, `PooledPriceNewsLSTM(..., use_gate=True, ...)`).

**G0 vs G1 differ only by one message-passing layer:**
- `self.message_passing = _ResidualMessagePassing(...) if use_gnn else None` (`models.py:176`).
- G0 = `use_gnn=False` → message passing OFF → output is just `head(base)`.
- G1 = `use_gnn=True` → `base = base + self.message_passing(base, adjacency, presence_mask)`
  (residual GAT-style aggregation, `_ResidualMessagePassing.forward`).
- `run_pilot.run_graph_screening` builds both from the same checkpoint:
  `use_gnn = name == "G1"` for `name in ("G0", "G1")`.

**Conclusion:** G0 is the graph-OFF equivalent of **P3** (the price+news+per-ticker-gate model).
G0/G1 share P3's encoders/gate/head (frozen); G1 additionally trains a small residual
message-passing projection on top of the frozen P3 node embeddings. G0 has **no trainable
parameters** (everything frozen); G1's only trainable parameters are the message-passing
projection.

**Important caveat — it is a *fresh* P3, not the screening P3.** The P3 that feeds G0/G1 is
rebuilt specifically for the graph run: `build_graph_bound_p3_warm_start` (1 epoch) →
`build_graph_safe_p3_checkpoint` (1 refinement epoch), both trained **only on graph-bound
samples** (`sample.key.target_date <= graph.train_end_date`, `run_pilot.py:130,180`), with
`dropout=0.0`. The screening P3 in the P0–P3 comparison is trained on the **full** pooled train
manifest (73,026 samples) for **5 epochs** with `dropout=0.2`. So even G0 is not numerically
identical to the screening P3 — it is a differently-trained P3 on a restricted training subset.

## Question 2 — Why do the metrics differ from P2/P3?

There are **two distinct G0/G1 runs**, and the answer differs sharply between them.

### Reference values (seed 42, horizon 5, validation only)

Pooled P0–P3 screening (`a1_pooled_seed42/h5/validation_comparison.json`, epochs=5):

| cfg | mse | rmse | r2 | qlike | dirAcc |
|-----|-----|------|----|-------|--------|
| P2  | 2.219e-06 | 0.0014896 | 0.7333 | 0.5082 | 48.32 |
| P3  | 2.228e-06 | 0.0014927 | 0.7322 | 0.5087 | 48.52 |

**First G0/G1 run** — `pooled_news_gnn_g0g1_2026-08-08_154500_seed42` (15:45, intersection manifest,
pre-positivity):

| cfg | mse | rmse | r2 | qlike | dirAcc |
|-----|-----|------|----|-------|--------|
| G0  | 6.815e-06 | 0.0026106 | 0.6997 | 0.8388 | 49.24 |
| G1  | 8.120e-06 | 0.0028496 | 0.6421 | **4.3811** | 47.67 |

**Later masked G0/G1 run** — `pooled_news_gnn_masked_g0g1_2026-08-08_212959_seed42` (21:29, masked
manifest, with positivity):

| cfg | mse | rmse | r2 | qlike | dirAcc | present_val_nodes | nonpos_rate |
|-----|-----|------|----|-------|--------|-------------------|-------------|
| G0  | 2.145e-06 | 0.0014645 | 0.7422 | 0.5093 | 48.85 | **14418** | 0.0 |
| G1  | 2.126e-06 | 0.0014579 | 0.7446 | 0.5082 | 49.09 | **14418** | 0.0 |

The masked run's `present_validation_node_count = 14418` is **exactly** the pooled P2/P3 validation
sample count (`P3/screening_manifest.json` → `ordered_keys.val = 14418`). Both use the same
`evaluate_records(records, store)` path (`run_pilot.py:614`) with the same per-ticker
`StandardScaler` inverse-transform. So the masked G0/G1 evaluate on the **identical 14,418
validation observations** as P2/P3 — the metrics are close, and the residual differences come only
from the differently-trained graph-safe P3 backbone + positivity + (G1) message passing.

### Ranked list of REAL causes of the difference (with magnitudes)

1. **Different graph manifest → different eval population (dominant for the first run).**
   The first run used the default **intersection / common-date** manifest
   (`_build_graph_manifest_for_mode` → `build_graph_manifest`, `graph_mode` default
   `"intersection"`), which keeps only synchronized dates where the fixed node set is present.
   That is a much smaller and different population (common-date train ≈ 9,606 total vs pooled
   73,026; see `docs/reports/2026-08-09_pooled_convergence_rootcause.md:71-72`). Effect: MSE
   ~6.8–8.1e-06 vs pooled ~2.2e-06 (≈3–4×), r2 0.70/0.64 vs 0.73. The later **masked** manifest
   (`build_masked_graph_manifest`, availability-aware union of dates: snapshot_count 6470, distinct
   dates 4941, val snapshots 1237) recovers exactly the 14,418 pooled val observations, and its
   metrics collapse back onto P2/P3 (within ~1e-8 MSE / ~0.001 qlike).

2. **No positivity floor in the first run (explains the QLIKE blow-up).** The positivity floor
   (`POSITIVITY_EPSILON`, `_apply_positivity`, `configure_positivity`) was committed at **16:03**
   (`8055413`), *after* the 15:45 first run. Without it, G1's message passing widens the normalized
   prediction variance so its lower tail denormalizes to non-positive volatility, and QLIKE
   (which divides by the prediction) explodes: **G1 QLIKE = 4.381**, G0 QLIKE = 0.839, vs pooled
   ~0.508. In the later masked run the floor is active and `nonpositive_prediction_rate = 0.0`, so
   G0/G1 QLIKE is back to ~0.508–0.509. This is a G0/G1-vs-P2/P3 difference (P2/P3 apply no floor)
   and, in the first run, a pure artifact.

3. **G0/G1 use a different P3 checkpoint than the P0–P3 screening.** The graph-safe P3 is retrained
   only on graph-bound samples (`target_date <= graph.train_end_date`), 1 warm-start + 1 refinement
   epoch, `dropout=0.0` — not the full-train, 5-epoch, `dropout=0.2` screening P3. So G0 (frozen P3
   + positivity) is not numerically identical to screening P3 even on the same observations. On the
   masked manifest this residual is small (G0 mse 2.145e-06 / r2 0.742 vs P3 2.228e-06 / r2 0.732 —
   marginally *better*, well within seed noise).

4. **Message passing (G1 only).** G1 adds the residual `base + projection(softmax(adj) @ base)`
   over the frozen embeddings. In the first (intersection, no-floor) run this widened variance and
   *hurt* every metric (paired_delta val-loss +0.110, QLIKE 0.84→4.38). In the masked run it is
   roughly null / marginally positive (paired_delta +0.0024 val-loss; qlike 0.5093→0.5082,
   r2 0.742→0.745). Consistent with the graph-null finding in project memory.

5. **Loss aggregation weighting (affects `validation_loss`, not the reported metrics).** G0/G1's
   `validation_loss` is a present-node-weighted per-snapshot MSE on the normalized scale
   (`_graph_validation_loss`, `_mean_snapshot_mse`), which is not comparable to the pooled flat
   per-sample MSE. But the *reported* `validation_metrics` come from the shared
   `evaluate_records` over the flat record list, so the metric formulas themselves are **not** a
   source of difference — only which records enter is.

6. **Epochs — minor / mostly irrelevant.** Pooled screening = 5 epochs; graph G0/G1 ran 5 epochs
   (train_losses length 5). But G0 has no trainable parameters, so its epoch count is inert; G1's
   epochs only tune the message-passing head. The graph-safe P3 backbone was fixed at 1+1 epochs
   regardless. Epoch count is a real config difference but a weak driver of the metric gap.

7. **Seed — NOT a cause for the matched comparisons.** Both the pooled and graph runs above use
   seed 42 (`screening_metadata.json` seed=42; graph run `--seed 42`). The seed is matched, so it
   does not explain the difference. (Full seed sets 42/123/2026 exist for both.)

### Verdict — apples-to-oranges vs fair

- The **first G0/G1 run vs P2/P3 is apples-to-oranges**: it changes the eval population
  (intersection/common-date, a different and much smaller set), the backbone (restricted graph-safe
  P3), *and* lacks the positivity floor. Its large metric gap (MSE ~3×, QLIKE up to 4.38) is
  dominated by causes #1 and #2 and should not be read as "the graph model is worse than P2/P3."
- The **later masked G0/G1 run vs P2/P3 is a near-fair comparison**: G0/G1 evaluate on exactly the
  same 14,418 validation observations via the same scaler/metric path, and the numbers land on top
  of P2/P3 (all differences within seed noise; G1 message passing ≈ null). This is the run that
  supports the graph-null conclusion.

### What a fully fair comparison would require

1. Same eval population — use the **masked** (union-date, present-node) manifest so G0/G1's 14,418
   present val nodes equal the pooled P2/P3 val samples (already achieved in the 21:29 run).
2. Same positivity handling on both sides (either floor both, or floor neither) — currently only
   G0/G1 floor, P2/P3 do not; the floor is inert at nonpositive-rate 0 on the masked manifest, so
   this is not biting there, but it should be stated.
3. Same backbone provenance — either evaluate G0 against the *same* graph-safe P3 (so G0 is the
   exact graph-off control for G1, which it already is), and compare that graph-safe P3 to the
   screening P3 separately; or retrain a screening-equivalent P3 (full train, 5 epochs, dropout
   0.2) as the graph backbone. Comparing G0/G1 to the *screening* P2/P3 mixes a backbone change
   into the graph on/off contrast.
4. Matched seeds (already done: 42/123/2026) and report multi-seed mean±std with a paired test
   (the G1−G0 `paired_delta` is the clean within-run graph on/off effect: +0.0024 val-loss on the
   masked seed-42 run, i.e. graph slightly hurts / is null).
